# AWS X-Ray

## Overview
- Service that collects data about **distributed application requests** and provides **tracing, visualisation, and analysis**.
- Solves the problem of **debugging microservices** — multiple loosely coupled components make it hard to trace a single request end-to-end.
- Keyword: **distributed tracing / microservices debugging → X-Ray**.

## Core Concepts

### Trace
- A **trace** collects all segments generated by a single request as it travels through your application.
- Each trace has a unique **Trace ID**.

### Segment
- A **segment** is data about the work done by a **single service/resource** for one request.
- Includes: service name, request/response data, start/end time, errors/faults.

### Subsegment
- A **subsegment** provides granular detail within a segment (e.g., a downstream HTTP call, a DynamoDB query).

### Service Map
- X-Ray generates a **service map** — a visual representation of your application's components and their relationships.
- Color-coded health indicators:
  - **Green** = OK
  - **Yellow** = throttled/slow
  - **Red** = errors/faults
- Helps identify which component is the bottleneck or source of errors.

### Sampling
- X-Ray does **not record every request** by default — uses **sampling** to reduce cost and overhead.
- Default: 1 request/second + 5% of additional requests.
- Custom sampling rules can be defined in the X-Ray console.

### Annotations vs Metadata
| | Annotations | Metadata |
|--|-------------|----------|
| Type | Key-value pairs (string, number, bool) | Any object |
| **Searchable** | ✅ Yes — filterable in X-Ray console | ❌ No |
| Use case | Identifying/filtering traces | Adding context to a trace |

## X-Ray Daemon
- A **sidecar process** that listens on **UDP port 2000**, buffers segment data, and forwards it to X-Ray.
- Must be running on EC2, ECS (as a sidecar container), or Lambda (built-in).
- On ECS: run the daemon as a **sidecar container** in the same task definition.

## Integration Points
- **Lambda** — automatic tracing of Lambda function invocations (enable Active Tracing in function config).
- **API Gateway** — enable X-Ray tracing per stage.
- **Elastic Beanstalk** — enable via `.ebextensions` config or Beanstalk console.
- **EC2** — install X-Ray daemon manually or via User Data.
- **ECS** — sidecar container pattern.
- **EKS** — run daemon as a DaemonSet.

## X-Ray SDK
- Available for: **Java, Python, Node.js, Ruby, .NET, Go**.
- Wrap your application code with the SDK to generate segments/subsegments.
- Provides **middleware** for web frameworks (Express, Django, Spring) to auto-instrument HTTP requests.

## Workflow
```
App Request → X-Ray SDK instruments request → Segment data → X-Ray Daemon (UDP 2000)
                                                                    → X-Ray API → Service Map / Traces
```

## Exam Tips
- **Distributed tracing / microservices performance** → X-Ray.
- **Service map** shows the topology and health of your application visually.
- **Annotations** are searchable; **metadata** is not.
- X-Ray **daemon** listens on UDP 2000 — required on each host/container.
- Lambda has **built-in X-Ray daemon** — just enable "Active Tracing" in the function config.
- Sampling controls cost — not every request is recorded by default.
- X-Ray ≠ CloudWatch — X-Ray traces requests across services; CloudWatch monitors metrics/logs.
